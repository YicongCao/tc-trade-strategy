对照最近一份预期文档，复盘实盘的实际表现。

这个命令是为手机上使用设计的：**先给结论，再给细节，正文里不要贴原始 JSON。**

## 第一步：找到要对照的预期文档

命令后面如果跟了日期（如 `/review 2026-07-30`），用那一天的；没跟参数就取 `notebooks/` 下最新的一份 `*-expectations.md`。

读完后**照抄它自带的「检查清单」和「判定口径」**，不要另起炉灶——预期文档里怎么写的就怎么执行。每份文档的清单可能不同，以文档为准。

如果 `notebooks/` 下没有任何预期文档，直接说明情况并停下，不要自己编一份预期再来对照。

## 第二步：拉实际数据

先 `list_user_strategies` 拿全部 strategy_ids，不要硬编码。然后按预期文档的检查清单逐条执行 MCP 调用。所有支持多个 id 的工具**一次传全部 id**，不要循环单个调。

注意几个容易出错的口径：

- `list_decisions` 不传日期默认只查最近 30 天，复盘时显式传 `date_from`
- 判断策略"跑没跑"看决策条数，不是看有没有成交——`hold` 和 `wait` 也是决策
- 区分 `execution_status`：`filled` 才是真实成交，`skipped` 是被再平衡毙掉的信号，两者绝不可混算
- 涨跌幅对照预期文档第一节冻结的基线价，不要用别的基准重算

## 第三步：逐条判定

对预期文档里的每一条预测给出 **命中 / 落空 / 无法判定**，按它写明的数值区间判，不要事后放宽标准。

**落空不等于坏消息**，有些预测落空恰恰说明系统比预想的好（比如预测会超额下单但实际按目标成交）。判定和评价分开写。

"无法判定"只用于前置条件没发生的情况（比如策略压根没运行，那么关于它下单量的预测就无法判定），不要用来回避明确落空的预测。

## 第四步：回答机制问题

预期文档里通常单列了几个待验证的机制问题。这部分比盈亏重要，**优先保证它们有答案**。

每个问题给出：观测到的事实、由此得出的结论、以及接下来该改什么。如果今天的数据不足以下结论，明说还缺什么、下一轮怎么才能拿到。

## 第五步：写复盘文档

写到 `notebooks/<美股交易日>-review.md`，结构：

1. **一句话结论**——今晚最重要的一件事是什么
2. **预测判定表**——逐条命中/落空/无法判定，附实际值
3. **机制问题的答案**
4. **实际盈亏**——各策略 `daily_pnl` 与合计，注明样本量不足以评价策略好坏
5. **新发现的问题**——按 P0/P1 分级，只列这次新出现的，已知问题不重复
6. **下一步动作**——具体到改哪个字段、调哪个工具，不要写"继续观察"

## 第六步：提交

按仓库的 git 规范提交并推送，不用再问。

## 回复格式

聊天里的回复控制在手机一屏能读完，按这个顺序：

1. 一句话结论
2. 预测命中率（如 `6/8 命中，1 落空，1 无法判定`）
3. 三行以内说清机制问题的答案
4. 如果有新的 P0，单独点出来
5. 最后给复盘文档的路径

**不要在回复里重复文档已有的表格**，也不要贴 MCP 的原始返回。
